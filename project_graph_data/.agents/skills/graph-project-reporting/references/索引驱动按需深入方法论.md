# 索引驱动、按需深入：图数据阅读方法论

## 核心理念

### ❌ 不要做的事

1. **不要批量读取所有节点**
   - ❌ `cat descriptions_output/description_summary/goal_*.txt`
   - 项目规模大时会信息过载，抓不住重点

2. **不要遍历整个图**
   - ❌ 逐个读取所有 goal、所有 issue、所有 work_block
   - 无法聚焦关键信息

3. **不要沿边游走（效率低）**
   - ❌ 读节点 JSON → 读边文件 → 读关联节点
   - 需要读3个文件才能理解一个关系

4. **不要假设固定的路径模式**
   - ❌ 认为所有问题都有"问题→目标→工作块→工作项→结果"的完整路径
   - 实际路径取决于节点的演变过程

### ✅ 要做的事

1. **从索引文件出发**
   - ✅ 先读 `changes/changelog.txt`
   - 识别关键节点ID

2. **按需读取节点**
   - ✅ 只读 changelog 中提到的节点
   - 不读全部节点

3. **从 history 提取关联节点**
   - ✅ 读节点的 history，直接看到关联节点ID
   - 只需读1个文件

4. **灵活深入**
   - ✅ 根据实际需要，按需读取关联节点
   - 不死板地按固定路径

## 数据层级与权威性

在深入了解文件读取策略之前，首先要理解数据的层级关系：

```
notes/ (原始工作笔记，最权威的数据源)
  ↓ 半自动生成
nodes/xxx.json (结构化图数据，关键信息摘要)
  ↓ 提取
descriptions_output/ (快速索引文件)
```

**关键认知**：
- **notes 是金标准**：人工撰写的原始工作记录，包含完整的思考过程、分析细节、技术决策
- **图数据是结构化摘要**：为了构建知识图谱而提取的关键信息，可能丢失细节
- **descriptions_output 是快速索引**：为了快速查看而提取的文本，用于概览和导航

**数据权威性**：
- 当需要了解细节时，notes 是最权威的数据源
- 图数据和 descriptions_output 用于快速导航和建立概览
- 所有图数据都是从 notes 半自动生成的
- 在正式汇报中，关键内容的引用优先级固定为：`notes > nodes > changelog`
- `changelog` 适合提供时间锚点和阶段切换信息，但不应单独承担重要结论的最终支撑，除非明确标注为弱证据

## 文件读取策略：两阶段方法

### 阶段1：快速索引和概览

**目的**：快速了解发生了什么、何时发生的、节点间的关联关系

#### 第一优先级：`descriptions_output/description_summary/xxx.txt`

**用途**：快速了解节点当前状态

**内容**：
- 第一行：`[状态: xxx | 完成度/解决度: xx%]`（goal 和 issue 有分数）
- 正文：节点的总体概括
- 末尾（如果是 work_item）：`工作笔记：路径` - 指向详细工作笔记

**示例**：
```
[状态: finished]

项目需求分析和实现难点评估工作项，已完成。进行了前期摸排工作...

工作笔记：jiedaidan_trace/wiki/preliminary_survy.txt
```

**何时读**：
- 建立概览时
- 快速了解节点状态时
- 了解"发生了什么"
- **查看 work_item 对应的工作笔记路径**

---

#### 第二优先级：`descriptions_output/history/xxx.txt`

**用途**：了解节点演变过程，提取关联节点

**内容**：
- 按时间倒序的历史记录
- 格式：`- [step_id] 变化过程；具体操作；关联节点（节点id）`

**示例**：
```
- [step12] 目标进度更新，completion_score从50提升到80；
  此目标被应急方案效果提升影响（结果节点id: result_emergency_plan_result）
- [step11] 目标进度更新，completion_score从40提升到50；
  此目标被应急方案验证结果影响（结果节点id: result_emergency_plan_result）
```

**何时读**：
- 需要了解节点演变过程时
- 需要提取关联节点ID时
- 需要深入追溯时
- 了解"何时发生的"

**关键**：从 history 中提取关联节点ID，继续按需读取

---

#### 第三优先级：`nodes/[类型]/xxx.json`（原始图文件）

**用途**：只在前两个文件无法满足需求时才读

**内容**：
- 节点的所有原始信息
- `description` 字段：完整文本（= summary.txt + history.txt）
- `summary` 字段：节点的简短摘要（一句话）
- `history` 字段：版本数组（用于回滚，包含 serialized_data）
- 其他字段：status, score, edges 等

**何时读**：
- 前两个文件无法满足需求时
- 一般极少用到

**重要区分**：
- ⚠️ `descriptions_output/description_summary/xxx.txt` ≠ JSON 的 `summary` 字段
- ⚠️ `descriptions_output/history/xxx.txt` ≠ JSON 的 `history` 字段
- ✅ 前两个文件是从 JSON 的 `description` 字段中提取出来的

---

### 阶段2：深入细节

**目的**：了解工作的具体过程、分析细节、技术决策依据

#### 唯一选择：`notes/xxx.txt`（工作笔记）

**用途**：获取权威的工作细节和完整的思考过程

**内容**：
- 详细的工作过程记录
- 具体的数据分析和案例
- 方案设计的推理过程
- 技术决策的依据
- 评测结果和指标

**何时读**：
- ✅ 需要了解具体的数据分析过程（如"分析了50个case的详细情况"）
- ✅ 需要了解方案设计的推理过程（如"为什么选择排序策略而不是判决策略"）
- ✅ 需要了解技术决策的依据（如"为什么不用向量召回作为最终结果"）
- ✅ 需要引用具体的数字、指标、案例
- ✅ 准备汇报材料，需要详细的支撑数据
- ✅ 需要了解"如何做的"和"为什么这样做"

**何时不需要读**：
- ❌ 只需要了解"发生了什么"（summary 足够）
- ❌ 只需要了解"何时发生的"（history 足够）
- ❌ 只需要了解节点间的关联关系（history 足够）

**关键问题**：如何定位要读哪篇笔记？见下文"定位工作笔记的方法"。

## 定位工作笔记的方法

**核心原则**：work_item 是定位 notes 的锚点

- **只有 work_item 节点有工作笔记**
- **work_item 的 summary 文件末尾会显示：`工作笔记：路径`**
- **定位 notes 的本质：在图上游走到相关的 work_item，读其 summary，看末尾的工作笔记路径**

**关键认知**：
- ⚠️ **通常需要多跳才能找到 work_item**
- ⚠️ **某条 history 记录里未必直接提到 work_item，需要沿着关系链追溯**
- ⚠️ **不同节点类型到 work_item 的距离不同**

**基本方法**：
```
1. 从当前节点的 history 中，识别关联节点（可能是 result、goal、work_block 等）
2. 读关联节点的 history 或 summary，继续追溯
3. 重复步骤1-2，直到找到 work_item
4. 读该 work_item 的 summary，查看末尾的"工作笔记：路径"
5. 根据文件名，读 notes/xxx.txt
```

**示例1：从 goal 追溯（2跳）**
```
goal 的 history：被 result_preliminary_survey 推动进度
↓
读 result_preliminary_survey 的 history
↓
看到：由 work_item_requirements_analysis 产生
↓
读 work_item_requirements_analysis 的 summary
↓
看到末尾：工作笔记：jiedaidan_trace/wiki/preliminary_survy.txt
↓
读 notes/preliminary_survy.txt
```

**示例2：从 issue 追溯（3跳）**
```
issue 的 history：触发了 goal_emergency_solution
↓
读 goal_emergency_solution 的 history
↓
看到：关联 work_block_emergency_solution_design
↓
读 work_block_emergency_solution_design 的 summary
↓
第一行显示：包含 work_item_emergency_plan_design
↓
读 work_item_emergency_plan_design 的 summary
↓
看到末尾：工作笔记：jiedaidan_trace/wiki/emergency_plan.txt
↓
读 notes/emergency_plan.txt
```

**容错**：
- 如果某个 work_item 的 summary 末尾没有"工作笔记"字段，说明该工作项没有详细笔记
- 这通常意味着这是一个相对简单的工作，summary 和 history 已经足够

## 按需深入的方法

### 基本流程

```
1. 读取节点的 summary → 了解当前状态（发生了什么）
2. 读取节点的 history → 了解演变过程（何时发生的）
3. 从 history 中提取关联节点ID
4. 【判断】是否需要了解工作细节（如何做的、为什么这样做）？
   - 需要 → 沿着关系链追溯到 work_item，读其 summary 末尾的工作笔记路径，读 notes/xxx.txt
   - 不需要 → 继续步骤5
5. 继续读取关联节点的 summary
6. 重复以上步骤，按需深入
```

### 关键原则

**1. 不要假设固定路径**
- 每个节点的 history 内容取决于其实际演变过程
- 不同节点的关联关系差异很大
- 不要死板地按"问题→目标→工作块→工作项→结果"这样的固定路径

**2. 根据需要灵活深入**
- 不是所有节点都需要深入
- 根据汇报/分析需要，选择性深入
- 聚焦关键节点

**3. 从 history 提取关联节点**
- history 中会提到关联节点ID
- 直接读取这些节点的 summary 或 history
- 不需要读边文件

**4. 按需深入到 notes**
- 不是所有 work_item 都需要读 notes
- 只在需要了解工作细节时才追溯到 work_item 并读 notes
- notes 是最详细的数据源，用于深入了解具体过程

## 常见深入路径（参考）

**重要提醒**：
- ⚠️ 以下路径只是**常见的参考**，不要死板地按照这些来
- ⚠️ 实际路径取决于节点的 history 内容
- ⚠️ 根据需要，灵活地从 history 中提取关联节点

---

### 路径1：追踪目标的完整工作循环

**目的**：理解目标是如何通过工作推进的

**核心循环**：
```
goal → work_block → work_item → result
  ↑                                 ↓
  └─────── 推动进度 ←───────────────┘
```

**操作步骤**：

1. **读 goal 的 history**，识别：
   - 触发来源：issue/event ID
   - 关联工作块：work_block ID（如果有）
   - 推动进度的 result：result ID + 进度变化

2. **读 work_block 的 summary**（按需）：
   - 第一行显示：包含哪些 work_item
   - 这是从 JSON 的 `work_items` 字段提取的

3. **选择关键 work_item，读其 history**（按需）：
   - 做了什么工作
   - 产生了哪个 result
   - 如何推动 goal 进度

4. **读 result 的 history**（重点）：
   - 最初由哪个 work_item 产生
   - 后续被哪些 work_item 持续更新
   - 每次更新如何推动 goal 进度

**关键洞察**：
- **result 是持续演变的**：一个 result 会被多个 work_item 持续更新
- **循环是持续的**：同一个 result 每次被更新都会推动 goal 进度
- **work_block 的 summary 第一行很重要**：直接显示包含的所有 work_item

**灵活应对**：
- 不是所有 goal 都有 work_block（有的 goal 没有组织工作块）
- 不是所有 work_item 都产生 result（有的是支持性工作）
- 根据实际 history 内容灵活调整

---

### 路径2：追踪问题及其应对

**目的**：理解问题如何被发现，以及如何应对

**操作步骤**：

1. **读 issue 的 history**（从下往上）：
   - 发现来源：哪个 work_item 发现的
   - 触发应对：触发了哪些 goal
   - 认识变化：resolution_score 和 description 的变化

2. **读被触发的 goal 的 history**（重要）：
   - goal 的 completion_score 如何变化
   - 哪些 work_item 和 result 在推动 goal

**关键洞察**：
- **issue 的 resolution_score 反映认识**：对问题本质的理解（可能上升或下降）
- **goal 的 completion_score 反映应对进度**：解决问题的工作进展（逐步上升）
- **问题认识的两种变化**：
  - 验证后发现没那么严重 → resolution_score 上升
  - 发现问题更复杂或性质转变 → resolution_score 下降

**容错做法（重要）**：
- ⚠️ **图数据可能有缺陷**：issue 的 resolution_score 可能没有及时更新
- ⚠️ **不要只看 issue 的分数**：要同时看被触发的 goal 的进度
- ⚠️ **goal 的进度更可靠**：反映了实际的应对工作进展
- 例如：issue 的 resolution_score 还是 0%，但它触发的 goal 已经推进到 80%，说明应对工作在进行中

---

### 路径3：追踪事件的影响

**目的**：理解外部事件如何影响项目

**操作步骤**：

1. **读 event 的 history**：
   - 事件发生的背景
   - 直接影响了哪些 goal

2. **读被影响的 goal 的 history**：
   - 在该 step 发生了什么变化
   - 是新建目标，还是调整时间线/意图

**关键洞察**：
- event 通常会触发新 goal，或调整现有 goal 的时间线/意图
- event 的影响是即时的，会立即反映在 goal 的 history 中

---

### 路径4：多跳深入（完整因果链）

**目的**：理解完整的因果链条，从触发到应对到结果

**典型多跳路径示例**：

**示例1：事件触发的完整链条**
```
event → goal → 子goal → work_block → work_item → result
  ↓                                                  ↓
  └──────────────────── 推动子goal完成 ←──────────────┘
                           ↓
                    推动主goal进度
```

**示例2：问题应对的完整链条**
```
issue → goal → work_block → work_item → result
  ↑                                       ↓
  └────── 深化认识 ←──────────────────────┘
```

**操作方法**：

1. **从触发点开始**（event 或 issue）：
   - 读其 history，找到触发的 goal

2. **追踪 goal 的演变**：
   - 读 goal 的 history
   - 识别：是否有子 goal、关联的 work_block、推动进度的 result

3. **深入工作层**（按需）：
   - 读 work_block 的 summary（看包含哪些 work_item）
   - 选择关键 work_item，读其 history

4. **追踪结果演变**：
   - 读 result 的 history
   - 看它如何被多个 work_item 持续更新
   - 看每次更新如何推动 goal 进度

**关键洞察**：
- **多跳路径揭示完整因果链**：从外部触发到内部应对到最终结果
- **子目标模式**：goal 可能创建子 goal，子 goal 完成推动主 goal
- **result 是关键枢纽**：连接 work_item 和 goal，记录完整演变过程
- **循环反馈**：work_item 的结果可能反馈到 issue，深化认识

## 总结

### 核心原则

1. **索引驱动**
   - 从 `changes/changelog.txt` 出发
   - 提取关键节点 ID
   - 不批量读取

2. **按需深入**
   - 先读 summary 了解当前状态（发生了什么）
   - 再读 history 了解演变过程（何时发生的）
   - 从 history 提取关联节点 ID
   - 需要细节时，追溯到 work_item 并读 notes（如何做的、为什么这样做）
   - 根据需要继续深入

3. **灵活应对**
   - 不假设固定路径
   - 根据实际 history 内容调整
   - 聚焦关键信息

### 关键发现

1. **result 是持续演变的**
   - 一个 result 会被多个 work_item 持续更新
   - 每次更新都可能推动 goal 进度

2. **issue 和 goal 的关系**
   - issue 的 resolution_score 反映认识变化
   - goal 的 completion_score 反映应对进度
   - 两者不一定同步，要同时看

3. **多跳路径的价值**
   - 揭示完整的因果链条
   - 理解从触发到应对到结果的全过程

4. **容错很重要**
   - 图数据可能有缺陷（如 issue 的分数未及时更新）
   - 要通过多个角度交叉验证
   - goal 的进度通常比 issue 的分数更可靠

5. **notes 是权威数据源**
   - notes 是原始工作笔记，最详细、最权威
   - 图数据是从 notes 半自动生成的结构化摘要
   - 需要了解工作细节时，追溯到 work_item 并读 notes
   - work_item 的 summary 末尾显示工作笔记路径

### 效率对比

**传统方法**（不推荐）：
- 批量读取所有节点 → 信息过载
- 沿边游走 → 需要读 3 个文件（节点→边→节点）
- 假设固定路径 → 不适应实际情况

**索引驱动方法**（推荐）：
- 从 changelog 提取关键节点 → 聚焦重点
- 从 history 提取关联节点 → 只需读 1 个文件
- 灵活按需深入 → 适应实际情况
- 需要细节时追溯到 notes → 获取权威数据源
